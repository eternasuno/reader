# Project Database

- The reader data lives in `<DATA_DIR>/reader.db` and Better Auth's data in `<DATA_DIR>/auth.db`. `DATA_DIR` defaults to `.data` relative to the process working directory and is created if missing (`apps/api/src/db/index.ts`). Keep the files separate: two connections to one file contend for SQLite's single write lock, and with synchronous `node:sqlite` a waiting writer blocks the event loop while the lock holder may need it to commit; Better Auth's dialect also opens a deferred `BEGIN`, which fails at once with `SQLITE_BUSY` on upgrade. Owner ids in `reader.db` are plain strings, so the split loses no constraint.
- At API startup, open the files only; do not generate or apply schema at runtime. Apply both Better Auth's migrations and the reader migrations through `pnpm --filter api db:migrate` (`apps/api/src/migrate.ts`), once during deployment, before the service starts.
- The reader store (`apps/api/src/store/`) uses `@effect/sql-sqlite-node` over Node's built-in `node:sqlite`, so no native module is installed: one connection, WAL, `BEGIN IMMEDIATE` for writable transactions and a 5 s busy timeout (library defaults). `store/client.ts` turns on `PRAGMA foreign_keys = ON` for that connection.
- Tables are `STRICT`; dates are INTEGER epoch milliseconds and booleans are 0/1. `decodeRows` in `store/sql.ts` drops NULL columns before schema decoding, so absent optional fields decode as none and HTTP JSON omits them instead of producing `null`, which browser schemas reject.
- Correctness does not come from an application-level lock: the `ReaderStoreConcurrency` semaphore is gone. SQLite allows one writer at a time with serializable transactions. Foreign keys `(owner, feed_id) -> feed(owner, id)` and `(owner, folder_id) -> folder(owner, id)` with `ON DELETE CASCADE` make removing a feed remove its items and removing a folder remove its feeds and their items, and they reject cross-owner references.
- Each `create` row is one `INSERT ... SELECT ... WHERE <parent exists> ON CONFLICT DO NOTHING RETURNING id`, or `INSERT ... VALUES ... ON CONFLICT DO NOTHING RETURNING id` without a parent, repeated per row inside one transaction (CM-PORT-3, CM-PORT-6): duplicates by id or unique key are skipped, never overwritten, and concurrent creates of one key leave one row. Guarded writes (`moveToFolder`, `rename`, `setExtractedContent`) are one `UPDATE ... WHERE <guard>`, with `RETURNING id` where the port must report whether a row changed. Do not turn either back into a check-then-write sequence.
- Bind every value through the `sql` tagged template (id lists through `inList` in `store/sql.ts`, which binds the whole list as one JSON parameter read with `json_each`: `sql.in` binds one parameter per element and fails past SQLite's variable limit, and the ports take unbounded lists) and interpolate only constant fragments such as fixed clauses and column names. Effect concatenates template fragments without whitespace, so an optional clause fragment must start with a space (``sql` AND read = 0` ``).
- Lists use database-side keyset paging on `id` descending, always scoped by owner (CM-OWN), filtered by `unreadOnly` in both lists and, for feed items, by `feedId` (`listByFeed`) or by the feeds whose `folderId` is the folder (`listByFolder`): the cursor is the `id` of the last returned row and the next page is the rows with a smaller id. `publishedAt` is display-only and belongs in no `ORDER BY`, keyset clause or index. Keep the keyset clause builder in one place.
- Indexes: feed `(owner, folder_id)`, `(owner, title, id)`; feed_item `(owner, id)`, `(owner, feed_id, id)`, `(owner, read, id)`; saved_page `(owner, id)`, `(owner, read, id)`. Choose them from the target queries and verify each with `EXPLAIN QUERY PLAN`; re-check with the real store SQL after changing paging or indexes, because existing measurements do not carry over. Include `owner` in every owner-scoped index and `feed` in feed-scoped ones.
- Unique constraints are `(owner, url)` on `feed`, `(feed_id, url)` on `feed_item`, `(owner, url)` on `saved_page` and `(owner, name)` on `folder`; `setting` is keyed by `owner` and every write method is one `INSERT ... ON CONFLICT (owner) DO UPDATE`. The port contract and the duplicate rules live in the `project-business` skill (CM-ID-6, CM-PORT); do not restate them here.
- The project is in development: do not write data migrations or compatibility paths for stored data. When the schema changes, edit migration `0001_reader` (`apps/api/src/store/schema.ts`) in place, delete the database files in `DATA_DIR` and run `db:migrate` again.
- `node:sqlite` is synchronous, so one write blocks the event loop while it runs. A benchmark (`apps/api/test/bench/refresh.ts`, 200 feeds x 100 items arriving at once) measured a refresh round of 1.2 s regular and 1.9 s heavy against 37 s and 82 s on the previous store, and "mark as read" about 1 ms against about 130 ms, but the loop stalled up to roughly 1.2 s during a round because each unbounded refresh fiber runs one synchronous write per loop turn; explicit yields did not help. Add no concurrency limit until running the application shows it is needed (`AGENTS.md`); issue #14 tracks this.
- `effect/sql` and `@effect/sql-sqlite-node` are unstable APIs; the root `tsconfig.json` allowlists them (`allowedUnstableApis`).

When database environment variables, deployment topology, or startup procedure needs confirmation, first read the relevant section of `README.md`; do not duplicate environment defaults or deployment lists in this skill.
