# Project Database

- At API startup, connect only to the configured SurrealDB/SurrealKV and select the namespace/database; do not generate or apply schema at runtime.
- Apply both the exported Better Auth DDL and reader-store schema through the project's existing `db:migrate` entry point.
- Normalize SurrealDB `NONE` results at the store boundary before domain decoding: selected fields can be present with value `undefined`. Remove those keys so Effect HTTP JSON encoding omits optional fields instead of producing `null`, which browser schemas reject.
- Apply the migration once during deployment, then start the service; do not put migrations into runtime startup, which can cause contention when multiple instances restart.
- Bind query values as parameters, including `LIMIT $limit`. Do not interpolate a value into SQL without a specific reason, even an internal numeric one, because later edits can route untrusted input there; interpolate only constant fragments such as fixed clauses and column names. On SurrealDB 4.0 binding `LIMIT` showed no meaningful speed difference from a literal.
- The project is in development: do not write data migrations or compatibility paths for stored data. The embedded engine's major version fixes the SurrealKV on-disk format (`@surrealdb/node` 3.2 embeds SurrealDB 4.0 and refuses directories written by 3.x). When a schema or engine change breaks existing data, delete the database directory and run `db:migrate` again.
- Lists order by `publishedAt DESC, <id> DESC` with database-side keyset paging; `afterBoundary` and `throughBoundary` in `reader-store-sql.ts` build the clauses. Keep their redundant plain `publishedAt` bound: without it SurrealDB 4.0 plans `Filter > IndexScan` from the head of the index and a deep page or refresh costs O(position) (24-56ms and 90-186ms at 15k-45k rows, against about 1ms and 5-6ms). A mixed ASC/DESC order cannot use a compound index, so do not reintroduce one.
- Indexes behind that order: `feed_item_order (publishedAt, itemId)` serves the unfiltered all-feeds scope (`feedId IN`, also above 32 ids, measured with 100 feeds), `feed_item_read_order (read, publishedAt, itemId)` the all-feeds scope with a `read` filter and the per-refresh `unreadCounts`, `feed_item_feed_order (feedId, publishedAt, itemId)` a single feed, `saved_page_owner_order (owner, publishedAt, pageId)` saved pages. Keep both global feed indexes: with only the `read`-prefixed one an unfiltered list plans `UnionIndexScan > Sort` (about 70ms at 15k rows), and with `read` as a trailing column the unread list is as slow as without it. The planner picks the right one without hints and the plans have no `Sort`. Without `feed_item_read_order` a rare unread filter (1% unread, 15k rows) scans until 31 unread rows are found (about 10ms), an unread `through` boundary deep in the list scans the whole table (70ms at 15k, 185ms at 45k) and `unreadCounts` reads every row (62ms at 15k, 210ms at 45k); with it these cost 1-3ms, 3-7ms and 7ms (45k: 22ms). The global feed indexes assume a personal deployment: a user who owns a tiny share of a large table makes the all-feeds scan walk the table (110 rows among 45k: 28-32ms), which would call for an `owner` column with `(owner, publishedAt, itemId)`; an `owner` column alone does not help the unread cases. `saved_page` has no `read`-prefixed index and was not measured with one.
- Re-measure with the real store SQL and `EXPLAIN` before changing paging or indexes; paging in application code measured slower than the database query even with an `owner` index.

When database environment variables, deployment topology, or startup procedure needs confirmation, first read the relevant section of `README.md`; do not duplicate environment defaults or deployment lists in this skill.
