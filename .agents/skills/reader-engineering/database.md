# Database (`internal/sqlite`)

Single SQLite database file (`<DATA_DIR>/reader.db`) using `modernc.org/sqlite`. Because this is a single-user, single-instance deployment, no separate auth database is needed.

## Connection, Pragmas & Startup Migration

- **File permissions**: `Open` creates the data directory (`0700` only when it creates the directory; an existing, possibly shared directory keeps its mode and the Docker image provides `0700`) and pre-creates the database file (`0600`) before opening pools or enabling WAL, and enforces `0600` on existing database, `-wal`, and `-shm` files on startup so stored secrets (SMTP password, Jina key, browser endpoint) are never group- or world-readable.
- **Per-connection pragmas**: SQLite `foreign_keys`, `busy_timeout`, and `synchronous` are connection-scoped. Configure them on **every** pooled connection via repeated modernc DSN `_pragma` parameters (`?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=synchronous(NORMAL)`) or a driver connection init hook — never by executing `PRAGMA` once on `*sql.DB`.
- **WAL & pools**: open the write pool (`SetMaxOpenConns(1)` with `_txlock=immediate` for `BEGIN IMMEDIATE`) first, execute `PRAGMA journal_mode = WAL`, then open the read pool (`MaxOpenConns > 1`). Note `SetMaxOpenConns(1)` serializes writes **within this Go process** only; concurrent external processes or multiple containers against the same file will still hit `SQLITE_BUSY` and are unsupported.
- **Single-instance lock**: on Unix, `cmd/reader` acquires a non-blocking exclusive `flock` on `<DATA_DIR>/lantern.lock` (`0600`) before opening SQLite or cleaning the EPUB spool directory, holding it until after workers stop and the store closes.
- **Startup migration**: goose **Go** migrations only, in package `internal/sqlite/migrations` (one file per version, e.g. `001_init.go`, collected by `All()` for `goose.WithGoMigrations`; no SQL files). They run through a `goose.Provider` on the write pool, tracked in `goose_db_version`, one transaction per migration (`RunTx`), before HTTP servers or workers start. Each migration is self-contained: DDL/DML as string constants and `database/sql` only, never importing `internal/domain` or repository code, so an applied migration cannot change meaning when application code does. Never edit an applied migration and preserve existing data; a schema change adds the next version. After migrating, `Open` runs `PRAGMA optimize` once on the write pool.

## Schema & Indexes

Single-user schema removes `owner` columns and composite `(owner, id)` constraints. Version 1 (`001_init.go`) is the whole schema; every table is `STRICT`.

- **Structure only**: the database enforces structure — column types, `PRIMARY KEY`, `FOREIGN KEY` + `ON DELETE`, `UNIQUE` where dedupe or `ON CONFLICT` needs it, `NOT NULL`, and `DEFAULT`s. No `CHECK` constraints, triggers, or partial unique indexes. All business rules live in Go and are validated on the write path in `internal/domain` (repositories trust validated input): enums (`provider`, `reader_mode`, `sort_order`, `smtp_security`, send `trigger`/`status`, refresh `status`), ranges (`retention >= 1`, schedule hour/minute), cross-field groups (SMTP fields, schedule fields set together), nonblank values, a single running send, a single running refresh per feed, and at most one `kindle_schedule` row per setting.
- **Structured values as columns** (the table-level case of the `SKILL.md` structured-values rule): a value with internal structure is stored as separate typed columns, never one formatted string (the Kindle schedule is `send_hour` + `send_minute` + `timezone`, not `"08:30"`), so each part validates on its own and a later display/format change cannot conflict with stored rows. Opaque external strings used whole (URLs, IANA zone names, sanitized error text) stay single `TEXT` columns.
- **Static vs runtime data**: static tables hold only user-owned entity fields and configuration (`folder`, `feed`, `feed_item`, `saved_page`, `setting`); runtime state lives in separate tables. Schedule tables (`feed_schedule`, `kindle_schedule`) hold the current runtime aggregates (due times, feed `updatedAt` / `failureCount` / `lastError`); record tables (`feed_refresh`, `kindle_send`) hold attempt history and the `running` rows that act as claims. Runtime aggregates are stored, not derived: they are updated in the same transaction as the event that changes them (refresh finish, Kindle claim, schedule save), never recomputed by aggregating history rows, because history is pruned.

Tables:

- **`folder`**: `(id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE)`. Index: `folder_name_id (name, id)`.
- **`feed`**: `(id TEXT PRIMARY KEY, url TEXT NOT NULL UNIQUE, title TEXT NOT NULL, site_url TEXT, icon_url TEXT, folder_id TEXT REFERENCES folder(id) ON DELETE SET NULL, reader_mode TEXT NOT NULL DEFAULT 'default', sort_order TEXT NOT NULL DEFAULT 'newest')`.
  - Note `ON DELETE SET NULL` ensures deleting a folder moves feeds to the top level (`FD-FOLDER-4`) atomically at the DB layer.
  - `site_url` and `icon_url` are the feed's own site link and image (`FD-PARSE-6`), replaced on each successful refresh. The feed row carries no refresh state (`feed_schedule` does).
  - Indexes: `feed_folder (folder_id)`, `feed_title (title, id)`.
- **`feed_item`**: `(id TEXT PRIMARY KEY, feed_id TEXT NOT NULL REFERENCES feed(id) ON DELETE CASCADE, url TEXT NOT NULL, title TEXT NOT NULL, description TEXT, content TEXT, extracted_content TEXT, published_at INTEGER, read INTEGER NOT NULL DEFAULT 0, UNIQUE (feed_id, url))`.
  - Indexes (verify every list variant, including `folder` queries, with `EXPLAIN QUERY PLAN`):
    - `(id)` PK covers `全部订阅` (`unread = false`)
    - `feed_item_read_id (read, id)` covers `全部订阅` (`unread = true`) and `unreadCounts` (`WHERE read = 0 AND id <= ? GROUP BY feed_id`: an index range scan plus a temp b-tree for the grouping)
    - `feed_item_feed_read_id (feed_id, read, id)` covers filtered single-feed unread lists
    - `feed_item_feed_id_url (feed_id, id, url)` covers unfiltered single-feed `ORDER BY id DESC|ASC` and the feed retention inventory
    - No standalone `(feed_id)` index (the two `feed_id` indexes above prefix it) and no `(read, feed_id, id)` index (it cannot cover `id <= boundary`); add an index only when `EXPLAIN QUERY PLAN` shows a plan regressing to a `SCAN`.
- **`saved_page`**: `(id TEXT PRIMARY KEY, url TEXT NOT NULL UNIQUE, title TEXT NOT NULL, description TEXT, content TEXT NOT NULL, published_at INTEGER, read INTEGER NOT NULL DEFAULT 0)`.
  - Index: `saved_page_read_id (read, id)`.
- **`feed_schedule`** (runtime): `(feed_id TEXT PRIMARY KEY REFERENCES feed(id) ON DELETE CASCADE, next_refresh_at INTEGER NOT NULL, last_success_at INTEGER, consecutive_failures INTEGER NOT NULL DEFAULT 0, last_error TEXT)`. Index: `feed_schedule_next (next_refresh_at, feed_id)` (covers the claim order, including the tie-break among feeds imported with the same due time).
  - One row per feed, inserted in the same transaction as the feed with `next_refresh_at = now` (`FeedRepository.Create`; `ImportOPML` only for inserted feeds, not skipped duplicates).
  - `FeedRepository.List` / `GetByID` / OPML export `JOIN` it for `UpdatedAt` (`last_success_at`), `FailureCount` (`consecutive_failures`), and `LastError` (`last_error`), with no aggregation over `feed_refresh`. `Create` returns the constant projection (`UpdatedAt` nil, `FailureCount` 0, `LastError` nil) because `INSERT ... RETURNING` cannot join.
  - `RequestRefresh` sets `next_refresh_at = now` when it is later (an unknown feed is not an error); a claim never changes it. `SucceedRefresh` / `FailRefresh` set `next_refresh_at = finishedAt + 30 min` (the worker computes it) and update the aggregates: success sets `last_success_at = finishedAt`, `consecutive_failures = 0`, `last_error = NULL`; failure increments `consecutive_failures` and sets `last_error` to the sanitized summary, leaving `last_success_at` (`FD-SCHED-3`). `ReleaseRefresh` and startup recovery leave the row untouched, so the feed stays due.
- **`feed_refresh`** (record): `(id TEXT PRIMARY KEY, feed_id TEXT NOT NULL REFERENCES feed(id) ON DELETE CASCADE, status TEXT NOT NULL, error TEXT, started_at INTEGER NOT NULL, finished_at INTEGER)`. Index: `feed_refresh_feed_id_id (feed_id, id)`.
  - One row per refresh attempt: `status` is `running` | `succeeded` | `failed` (domain constants), `error` is the sanitized summary on failures, `finished_at` is `NULL` while running.
  - `ClaimDueRefresh` inserts the `running` row in one write transaction for the oldest (`ORDER BY next_refresh_at, feed_id LIMIT 1`) due `feed_schedule` row that has no `running` row. This claim is the queue and the per-feed dedupe (`FD-SCHED-2`).
  - `SucceedRefresh` / `FailRefresh` finish it with `WHERE id = ? AND feed_id = ? AND status = 'running'` and write nothing when no row matches (feed deleted, outcome already recorded); `SucceedRefresh` also applies the sync (feed meta, new items, deletions) in the same transaction. `ReleaseRefresh` deletes the `running` row after an internal database error. `RecoverRunningRefreshes` (startup, before workers) marks every `running` row `failed` with `error = 'interrupted'`. Cancellation writes nothing.
  - Each finishing transaction (and recovery, per affected feed) prunes to the newest `10` finished rows per feed, never deleting `running` rows (`FD-SCHED-3`).
- **`setting`**: singleton row (`id INTEGER PRIMARY KEY`, `id = 1` seeded by the migration) storing `retention` (default `100`), `provider` (default `'direct'`), `jina_key`, `browser_endpoint`, SMTP fields (`sender_email`, `smtp_host`, `smtp_port`, `smtp_security`, `smtp_user`, `smtp_password`), `kindle_email`, and the schedule columns `send_hour`, `send_minute`, `timezone` (IANA name).
  - The three schedule columns are static configuration: all `NULL` while scheduled sending is off and all set while it is on (enforced in Go). The next send time lives in `kindle_schedule`.
- **`kindle_schedule`** (runtime): `(id TEXT PRIMARY KEY, setting_id INTEGER NOT NULL REFERENCES setting(id) ON DELETE CASCADE, next_send_at INTEGER NOT NULL)`. Index: `kindle_schedule_setting (setting_id)`.
  - A row exists only while scheduled sending is on, at most one per setting (enforced in Go; no `UNIQUE`). `SettingRepository.UpdateKindle` deletes it when the schedule is off; when the schedule is newly enabled or its hour/minute/timezone changed it sets `next_send_at = domain.NextKindleOccurrence(...)` (updating the existing row by `id`, or inserting one with `domain.NewID()`); an unchanged schedule leaves the row untouched (`KD-SCHED-1`). Unlike other repository writes, `UpdateKindle` re-validates the schedule before opening the transaction: an out-of-range hour or minute has no occurrence, so `NextKindleOccurrence` would never return while holding the only writer.
  - `SettingRepository.Get` reads it with `setting` in one `LEFT JOIN` snapshot as `Kindle.NextSendAt`, returned as stored (it may be in the past while overdue; nil while off). `ClaimDueSend` advances it in the claim transaction.
  - Keep occurrence math in `domain.NextKindleOccurrence` / `LatestKindleOccurrence`, which handle DST gaps and overlaps; never replace them with plain `time.Date`.
- **`kindle_send`** (record): `(id TEXT PRIMARY KEY, trigger TEXT NOT NULL, status TEXT NOT NULL, article_count INTEGER NOT NULL DEFAULT 0, book_count INTEGER NOT NULL DEFAULT 0, error TEXT, started_at INTEGER NOT NULL, finished_at INTEGER)`; `trigger` (`manual` | `scheduled`) and `status` (`running` | `succeeded` | `failed`) come from domain constants.
  - Pruned to the newest `20` completed rows (never deleting `running` rows) after inserting/completing a run, with no other exception (`KD-LOG-1`). On startup, `RecoverRunningOnStartup` marks any leftover `running` rows `failed` and prunes in the same transaction, before starting HTTP/schedulers.
  - `ClaimDueSend` / `ClaimManualSend` insert the `running` row in one write transaction after checking that none exists; `ClaimDueSend` also checks `kindle_schedule.next_send_at <= now` and configured delivery, and sets `next_send_at` to the next future occurrence (missed occurrences collapse into one catch-up).
  - `book_count` also guards receipts: `RecordBookAccepted(sendID, bookIndex, ...)` requires a `running` send, then in one transaction `book_count == bookIndex` sets `book_count = bookIndex + 1`, adds the book's articles to `article_count`, and marks its articles read; `book_count > bookIndex` is an already accepted book (no writes, no error); `book_count < bookIndex` is a skipped book (error). Bounded DB-write retries therefore never double-count or re-mark.

## Query Rules

- **Dates & booleans**: store timestamps as `INTEGER` epoch milliseconds; booleans as `0`/`1`.
- **Keyset paging**: `WHERE id < ?` (`DESC`) or `WHERE id > ?` (`ASC` for `oldest`), `ORDER BY id DESC|ASC LIMIT ?` (fetching `limit + 1` rows to compute `cursor`). `published_at` is never in `ORDER BY` or indexes.
- **Boundary snapshots**: list, unread-count, and read-all queries bind `id <= boundary` (the request's or minted `boundary`) alongside any keyset cursor predicate. `TestQueryPlansUseIndexes` (`internal/sqlite/db_test.go`) covers these queries with `EXPLAIN QUERY PLAN`; new paged or bulk queries must follow the same binding.
- **Unbounded ID lists**: pass ID slices via `json_each(?)` rather than building dynamic `IN (?, ?, ...)` placeholders to avoid SQLite parameter limits.
- **Atomic writes**: use `INSERT ... ON CONFLICT DO NOTHING RETURNING id` and `UPDATE ... RETURNING id` instead of check-then-write sequences. A check that spans statements (claiming a refresh or send) runs in one write transaction; the single write connection with `BEGIN IMMEDIATE` makes check-then-insert atomic.
