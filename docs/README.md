# Documentation index

This directory specifies the behavior of the reader: a self-hosted read-later and feed reader. A user saves web pages to read later, subscribes to feeds, and reads the articles in one place.

The specs describe the **target** behavior and structure, and state it without reference to the present code. The business core was rewritten from them on 2026-11-11 and follows them now. "The current code" at the end records how the earlier code differed and lists outer-layer behavior that must be kept.

## Overview

The business core (`packages/business`) is split into four domains. Each domain owns its entities, its use cases and the ports it needs.

| Domain    | What it owns                                                                                                                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Feed      | Subscriptions and their items: preview, subscribe, refresh, item selection and retention, listing, extraction, read state, unread counts, unsubscribe                                                    |
| SavedPage | Pages saved to read later: add a link, save a feed item, listing, read state, removal, unread count                                                                                                      |
| Setting   | Per-user settings: article retention and how pages are fetched (Jina or a browser service)                                                                                                               |
| Common    | Rules and helpers used by more than one domain: URL normalization, article values, ids, fetching and extracting an article, cleaning feed text, paging and cursors, the clock, the shared port contracts |

Accounts, sessions and the HTTP and browser layers are outside the business core. They are described by scenarios only (`features/account.feature`).

Dependencies between domains point one way and have no cycles:

```text
SavedPage -> Feed -> Setting -> Common
```

SavedPage reads feed items to save a copy. Feed reads the retention setting to decide how many items to keep. Every domain may use Common.

## Terms

| Term          | Meaning                                                                                                                                                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner         | The signed-in user a row belongs to. Taken from the session; the scheduler takes it from the stored feed                                                                                                                               |
| Feed          | A subscription of one owner to one source address                                                                                                                                                                                      |
| Source        | The remote document (RSS, Atom, JSON Feed) a feed points at                                                                                                                                                                            |
| Entry         | One article as listed by a source, before it is stored                                                                                                                                                                                 |
| Feed item     | A stored entry. The specs say "item"; the scenarios say "article", which is the word the user sees                                                                                                                                     |
| Saved page    | A page in the read-later list. The scenarios also say "page"                                                                                                                                                                           |
| Retention     | N, the number of items a feed keeps                                                                                                                                                                                                    |
| Sync          | Bringing a feed's items in line with its source. Refresh is fetch plus sync, always run through the scheduler's refresh queue                                                                                                          |
| Arrival order | The order feed items and saved pages are listed in: `id` descending. Ids are made in creation order, so the top is the newest. A row's id never changes while it is stored, so paging never repeats or skips a stored row (CM-PAGE-10) |
| Boundary      | Where outside data becomes typed values: HTTP handlers, adapters (fetchers, feed parser, article extractor, sanitizer) and configuration                                                                                               |
| Port          | An interface business depends on. An adapter implements it and is provided by dependency injection                                                                                                                                     |

## Principles that apply everywhere

| Principle                                                      | Meaning                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Parse at the boundary                                          | Parsing and validation happen where outside data enters: HTTP input, adapter outputs and configuration. Past those boundaries, branded values are trusted and never re-validated                                                                                                                             |
| Entities carry the rules of their values                       | URL normalization and article values live in the entity schemas, not in use cases                                                                                                                                                                                                                            |
| An operation that only forwards one port call gets no use case | Find one, mark, remove, unread counts and list feeds are direct port calls; their rules are stated as port contracts (CM-PORT)                                                                                                                                                                               |
| Ownership by owner                                             | The owner comes from the session. Every read and write is scoped by owner, so foreign ids behave as absent                                                                                                                                                                                                   |
| Ids and duplicates                                             | Every id is a version-7 UUID made by the entity schema's `id` default (`Model.UuidV7WithGenerate`) when a row is built, increasing within the process. A URL is unique per owner (feeds, saved pages) or per feed (items) through a unique index, so duplicates are caught by `create` without a lookup race |
| Numbers of the deployment are not business values              | Use cases define no numbers. The range and default of a business value belong to its entity type (for example `Retention`). Numbers of the deployment (page size, text-length limit, schedule) are parameters or come from injected configuration                                                            |
| Behavior is switched by injection, not by parameters           | The outer layer reads what it needs (for example the fetcher setting) and provides the matching adapter to the use case                                                                                                                                                                                      |
| Port contracts are business rules                              | Each repository port has one contract test suite that every implementation passes (CM-PORT)                                                                                                                                                                                                                  |
| A use case module holds every core function                    | `usecase/` holds pure functions and functions that need ports alike                                                                                                                                                                                                                                          |

## Documents

### `usecases/` — specifications

Each spec states entities, numbered rules, a table of use cases with input, output and errors, a table of errors, and the port contracts. Rules are numbered (for example `FD-SUB-1`) so tests, code and scenarios can point at them. A rule stated in `common.md` is referred to from the domain specs, not repeated.

| File                     | Prefix | Content                                                                                                                                                                                                                                                   |
| ------------------------ | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `usecases/common.md`     | `CM-`  | URL normalization, article values, ids, fetch-and-extract, text cleaning, paging and cursors, ownership, the clock, the functions, the errors and the shared port contracts                                                                               |
| `usecases/setting.md`    | `SET-` | Setting entity grouped by category, the rules of its value types (retention, Jina key, browser endpoint), setting the fetcher as a union by provider, clearing the Jina key, the "browser needs an address" invariant. Core logic only, no HTTP interface |
| `usecases/saved-page.md` | `SP-`  | Entity and id, add a link, save a feed item and what the copy takes, listing, read state, removal, unread count, port contract                                                                                                                            |
| `usecases/feed.md`       | `FD-`  | Entities and ids, fetch-and-parse helper, preview, subscribe, item selection and retention, import, sync, refresh, listing, find, extract, read state, unread counts, unsubscribe, scheduler, ports                                                       |

Reading order: `common.md`, `setting.md`, `feed.md`, `saved-page.md`.

### `features/` — reference scenarios in Gherkin

Scenarios written from the user's side. They are a reference and a guide for changes in the outer layers (HTTP handlers, adapters, front end). They are not the source of truth for rules: when a scenario and a spec disagree, the spec wins. A comment above a scenario gives the rule it exercises. Scenarios cover what a user or the system can observe; rules about values and helpers (`CM-URL`, `CM-ID`, `CM-HTML`, port contracts) are covered by unit and contract tests instead. The example table in `FD-SEL` is an illustration of the pure `selectItems` function: it is covered by that function's unit tests, not by scenarios. HTTP and form behavior that the specs leave out is described only here, under `@boundary` and `@ui`.

| File                          | Domain                                           |
| ----------------------------- | ------------------------------------------------ |
| `features/feed.feature`       | Feed                                             |
| `features/saved-page.feature` | SavedPage                                        |
| `features/setting.feature`    | Setting                                          |
| `features/account.feature`    | Accounts and sessions (outer layer, Better Auth) |

Tags:

| Tag         | Meaning                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------- |
| `@ui`       | Front-end behavior. Not a business rule                                                            |
| `@boundary` | Behavior at the HTTP boundary: parsing requests and shaping responses (for example hiding secrets) |
| `@system`   | Behavior with no user action, such as the scheduled refresh                                        |

## Decisions that shaped the specs

| Topic                      | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domains                    | Split by entity: Feed (with its items), SavedPage, Setting; shared logic in Common                                                                                                                                                                                                                                                                                                                                                                                     |
| Saved pages and feed items | Independent. Saving an item copies it; afterwards they never affect each other                                                                                                                                                                                                                                                                                                                                                                                         |
| Identity                   | Every id is a version-7 UUID made by the entity schema's `id` default (`Model.UuidV7WithGenerate`); there is no id port (CM-ID). Uniqueness is by URL, not by id: one feed per owner and URL, one item per feed and URL, one saved page per owner and URL (CM-ID-6, CM-PORT-6)                                                                                                                                                                                         |
| Saved page URL             | Required. Every feed item has a URL, so every item can be saved                                                                                                                                                                                                                                                                                                                                                                                                        |
| URL normalization          | In the entity schema: http and https only, tracking parameters removed, the fragment always removed, credentials allowed and never rejected by a fetcher. The standard URL serialization applies and nothing else. Pages of a site that routes by fragment collapse into one URL; this is accepted                                                                                                                                                                     |
| Sanitized text             | Stored description and content are always sanitized. Feed text is cleaned by business through the sanitizer port; extracted pages are sanitized by the extractor port                                                                                                                                                                                                                                                                                                  |
| Duplicates                 | An entry whose URL is already stored in that feed is not imported again; a saved page is detected by `findByUrl` before any fetching; the unique URL index decides concurrent requests inside `create` (CM-ID-6, CM-PORT-6)                                                                                                                                                                                                                                            |
| Listing                    | Feed items and saved pages by `id` descending, so the newest is on top; feeds by title, then `id`; `unreadOnly` boolean; page size from the caller                                                                                                                                                                                                                                                                                                                     |
| Cursor                     | The `id` of a row, handled as a structured value in business; encoding is a boundary concern; changing scope or filter starts a new list                                                                                                                                                                                                                                                                                                                               |
| No background list reload  | No refresh-through operation and no background reload; reload means listing again from the first page. A row's id never changes while it is stored and paging never repeats or skips a stored row; a row created meanwhile normally has a larger id and shows when the caller lists again from the first page (CM-PAGE-10)                                                                                                                                             |
| Read state                 | Marking by id list, by feed, and all, each stated separately; unknown ids are ignored; everything is idempotent                                                                                                                                                                                                                                                                                                                                                        |
| Retention                  | By the source's own order: the first N listed entries are retained; stored items the source no longer lists are kept in list order from the top. The rest is removed from the bottom of the list. Read state plays no role. One rule serves a new feed and a refresh                                                                                                                                                                                                   |
| Missing publish time       | For display only. The extractor and the feed parser report it as none and nobody invents one; it takes no part in ordering, retention or paging                                                                                                                                                                                                                                                                                                                        |
| Source changes             | Stored items are never updated from the source; a row's id never changes while it is stored, so a source that reorders or edits entries already stored is not followed; items the source drops stay until retention removes them (CM-PAGE-10)                                                                                                                                                                                                                          |
| Subscribing                | Create the feed with the title the user saw in the preview, then enqueue it in the refresh queue. Nothing is fetched in the request; the items appear after the first refresh                                                                                                                                                                                                                                                                                          |
| Feed refresh               | Only through the scheduler's refresh queue: each feed has at most one refresh, queued or running, and a request for a feed that already has one in either state is dropped; failures are logged and invisible to the user; the writes are not atomic; a feed removed meanwhile is not an error, and items of a missing feed are skipped, so nothing is left behind. Subscribing to the same URL again gives a new feed with a new id, enqueued on its own (FD-UNSUB-5) |
| Scheduler                  | In the application, not in business. A queue of per-feed refreshes; the refresh interval and the number of parallel jobs are its own configuration                                                                                                                                                                                                                                                                                                                     |
| Unsubscribing              | Idempotent; removes the feed and its items; saved pages stay                                                                                                                                                                                                                                                                                                                                                                                                           |
| Not found                  | There is no feed-not-found error: an unknown feed lists as empty and refreshes as a no-op. `FeedItemNotFound` only where an operation cannot go on without the item (extract, save to read later)                                                                                                                                                                                                                                                                      |
| Repository ports           | Generic patches (`update`, `updateByFeeds`, `updateAll`) rather than one method per intention; immutable fields are never in a patch; the boundary limits what may be patched                                                                                                                                                                                                                                                                                          |
| Limits                     | The text-length limit is the `maxTextLength` parameter of `refreshFeed`, passed by the application, and counts Unicode code points; the page size is a positive parameter bounded at the boundary                                                                                                                                                                                                                                                                      |
| Settings                   | Grouped by category; setting the fetcher is one operation with a union by provider; a stored key or address is kept when omitted; the Jina key can be cleared after confirmation; the browser address can only be replaced; the key and the address are redacted and never sent to the browser, which learns only whether each is configured                                                                                                                           |
| Provider choice            | The outer layer reads the owner's fetcher setting and injects the matching `WebpageFetcher`. Business takes no provider or owner parameter for fetching                                                                                                                                                                                                                                                                                                                |
| Entries without a URL      | An entry with no valid URL, after resolving it against the source, is not imported. Every item has a URL, so every item can be saved                                                                                                                                                                                                                                                                                                                                   |

## Target code layout

The code is grouped by layer first. `entity/` and `usecase/` are split by domain inside; `port/` is flat, because the port interfaces are generic and a domain split only adds paths.

```text
packages/business/src/
  entity/
    common/        normalized-url, owner-id, article, option-from-optional-non-empty
    feed/          feed, feed-item
    saved-page/    saved-page
    setting/       setting, retention, fetcher
  port/            webpage-fetcher, html-parser, document-sanitizer, article-extractor,
                   feed-repository, feed-item-repository, feed-parser,
                   saved-page-repository, setting-repository
  usecase/
    common/        fetch-and-extract, errors
    feed/          fetch-parsed-feed, preview-feed, subscribe-feed, refresh-feed,
                   list-items, extract-item, errors
    saved-page/    add-saved-page, save-feed-item, list-saved-pages, errors
    setting/       set-fetcher, errors
  index.ts         re-exports every module
```

Rules for the layout:

- `entity/` holds only business entities and the value types of their fields. Paging, cursors, queries, use-case inputs and values a port returns (`ParsedFeed`, `ExtractedArticle`) are not entities.
- `port/` holds the port interfaces, together with the types they take and return and the port's own error. A capability Effect already provides as a service is used directly, not wrapped in a port: fetching a feed source uses `HttpClient` from `effect/http`.
- A deployment value a use case needs (the text-length limit) is a plain parameter, not a port.
- `usecase/` holds every core function of the domain, whether it is pure or needs ports. A function called by only one use case is part of that use case's module, not a module of its own (the sync, selection and text cleaning are inside `refresh-feed`), and a few lines shared by two use cases are repeated rather than extracted. The errors a use case raises live in `usecase/<domain>/errors.ts`.
- A layer or domain with nothing to put in a folder omits it.
- Tests mirror the layout: `test/entity/<domain>/`, `test/usecase/<domain>/` and a flat `test/port/`. `test/port/` holds the contract suite of each repository port and its in-memory double; `test/testing.ts` exports them as `@reader/business/testing`, so every implementation runs the same suite.
- Imports follow the dependency direction `SavedPage -> Feed -> Setting -> Common`. Inside the package, modules import each other by relative path.
- Adapters, HTTP handlers, the scheduler and the front end stay in their packages and apps; they import from `@reader/business` only.

## The current code

The rewrite has landed: the code follows the specs and the layout above. The two tables below are kept as the record of what the rewrite changed; the file paths in them refer to the earlier code and many no longer exist. "Outer-layer behavior to keep" still applies.

The business core is rewritten from the specs, not migrated step by step. The current code is the reference for details the specs leave to the implementation, so this section says what to carry over and where it must not be copied. It is the only place in `docs/` that describes the current code. The lists are a summary, not exhaustive.

### Outer-layer behavior to keep

These behaviors live outside the business core. The specs do not state them, but they must survive the rewrite:

- HTTP error status and tag mapping, and the front end's whitelist of error tags (`apps/web/src/lib/library-error.ts`).
- The Origin check that rejects cross-site non-GET requests with 403 (`apps/api/src/middleware/origin.ts`).
- Feed parser behavior: RSS, Atom, RDF and JSON Feed; plain-text Atom and JSON `content_text` escaped; `DOCTYPE` and `ENTITY` declarations rejected (`apps/api/src/adapter/feed-parser.ts`).
- Request limits: a URL of at most 4096 characters and at most 5000 ids per batch (`packages/api/src/common.ts`).
- The shared browser-fetch concurrency of 2 with a 40-second timeout (`packages/webpage/src/webpage-fetcher.ts`).
- The front end's optimistic read-state update with rollback on failure (`apps/web/src/pages/library-read.ts`).
